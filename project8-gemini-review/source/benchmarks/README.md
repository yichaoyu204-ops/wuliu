# 采购账单跨格式工程回归

本目录提供 20 组虚构交易、40 个可实际上传的输入文件。每个 `pairs/SIMxx` 目录包含一份供应商账单（invoice）和一份独立采购依据（baseline）。所有金额、费用名、运单、主体及业务差异均为测试而构造。原计划要求的 20 组真实历史账单仍单独在 `../validation/` 登记。

## 使用样本

1. 打开物流对账应用，从同一编号目录分别选择账单和采购文件。不要一次混合多组。本测试有意复用虚构运单号。
2. 选择 SIM01 练习相等金额，SIM02 练习多收，SIM03 查看文字 PDF 人工确认前后的变化，SIM14 或 SIM15 查看对侧文件无法解析的提示。
3. 将结果和 `answer-key.json` 中同号样本对照。金额差额为账单减采购基准，标注中的整数按分计。未能比较的行使用 null。

## 重跑

生成输入和事先写定的逐项预期只需要 Python 3 标准库。工程回归使用 Node.js、Playwright Core 及相应 Chromium。

```sh
python benchmarks/generate.py
node benchmarks/run.cjs
```

从项目根目录执行。可用环境变量 `BENCH_PLAYWRIGHT` 指定 Playwright 模块路径，`BENCH_CHROMIUM` 指定浏览器可执行文件。浏览器用本地拦截的 HTTPS 请求读取项目里的 JSZip、PDF.js 和应用代码，不需要监听端口或访问公网。

## 本轮结果

11 月 26 日，20/20 组符合本测试集预期。CSV 16 份、XLSX 15 份、可选中文字的 PDF 9 份。18 组具有可读取的表头，另 2 组刻意破坏一侧表头，导入阶段均产生文件级人工核查提示。276 个可解析的字段与生成输入的原值一致，全部保留字段位置。PDF 中 54 个已识别字段均标为待人工确认。

对每个成功读取的字段，测试脚本先检查原始值和溯源，再模拟按原文确认后运行金额核对。`raw` 记录应用正式入口 auditDocuments 的直接导入结果。`after` 逐行核实来源记录、核对状态与金额。对于文件级失败样本，检查无解析行、有明确文件提示、无数值差额，并验证单侧残留项统一显示“对侧资料待核”。逐组结果在 `regression-results.json`。

这组人工设计的边界样例覆盖币种/单位不符、正负/零额、重复、乱序、两边缺项、信用调整、空金额、未知表头及精度问题。它没有真实客户、运价、实付或时间记录，无法估计实际正确率、节时或支付意愿。
